## Findings by severity

### Major
- **tjs-lang keeps its own copy of the old unwrap policy (confirmed, blast-radius).** tjs-lang still has `x?.schema ?? x` in src/types/Type.ts:181/363/416/450, and `'schema' in x` duck-typing at Type.ts:205 and :810 and in runtime.ts ~1355/1603/1622. That leaves two problems:
  - The #1390 accept-all fix doesn't reach tjs users, because tjs-lang does its own unwrapping.
  - With `^1.5.1`, the next update pulls in 1.12. After that, `typeParamToCheck` with `{name:'', schema:{}}` rejects everything, and `Schema.isValid(data, {schema:{type:'string'}})` on a JSON-parsed envelope now returns false. It validated correctly in 1.5.1.
  - The break is intentional and documented, so it doesn't block this repo. It needs follow-up in the other repo.

### Minor
- **checkExamples gives wrong results on nested nodes that have a stray `schema` key (confirmed, correctness).** src/contract.ts:717 calls `validate(x, s)` on each subschema node separately, so the refusal that is meant only for the root fires on nested nodes too. For `{type:'object', properties:{a:{type:'string', schema:true, examples:['x'], $counterexamples:['y']}}}`:
  - Example `'x'` is reported as rejected, and the reason says `root:` instead of naming the nested path.
  - Counterexample `'y'` is counted as held, although the full-tree validate accepts it.
  - `checkExamples({type:'string', schema:true, $counterexamples:['ok-string']})` returns `[]`. In 1.11.0 that counterexample was flagged, so a visible lint failure has become a silent pass.

  The verifier also found that `anyOf` branches get the refusal while `properties` children don't. So whether a stray key is refused depends on where it sits, in validate itself as well as in the lint.
- **`s.union(s.string)` / `s.tuple(s.string)` throw a raw `schemas.forEach is not a function` (unverified, correctness).** The non-array guard calls `assertBuilder`, and a builder passes that check. #1391 set out to remove exactly this kind of raw internal error. The completeness pass independently reported the same thing.
- **The return contract of the public `unwrap` changed (unverified, correctness).** It can now return the `AMBIGUOUS` Symbol, and the BREAKING entry in the CHANGELOG doesn't say so.
- **Bundle grew +400 B gz (+4.7%) with no CHANGELOG note (unverified, efficiency).** The validate/s import grew from 3.6 to 3.9 kB. The growth is justified (brand plus guards); only the disclosure is missing.
- **README migration table is broken (confirmed by reading, docs).** A blank line at README.md:33 splits off the `s.array({ type: 'string' })` row, which is the row documenting #1391. It renders as stray pipe text, not as part of the table.

### Nit
- **Internal symbols ship as public API (unverified, blast-radius).** `AMBIGUOUS` (marked `@internal`, but there is no stripInternal), `AMBIGUOUS_MESSAGE` and `unwrap` are exported through `export *` and the .d.ts. `BUILDER` and `isBuilder` are exported the same way. Only `BUILDER` and `isBuilder` are mentioned in the CHANGELOG.
- **`bun run pack` prints no size delta against the last release (unverified, efficiency).**

## Remediation (applied before the tag)

- **checkExamples / position-dependent refusal: FIXED at the root cause.** The refusal fired wherever the implementation re-entered the public `validate()`. That covered union branches, `filter`'s re-validation, a builder's own `.validate`, `M.func`, `agentContract` and `checkExamples`, not only in checkExamples. Probing found two worse cases than the review reported: `s.object(...).meta({schema:'x'}).validate(valid)` returned `false`, and `filter` refused the same builder. The fix splits `validate` (resolve + refuse the ambiguous root argument) from the internal `validateResolved` (already-resolved schema, no unwrap), and every internal caller now uses the latter. A stray `schema` key inside a tree is now ignored at every depth.
- **s.union / s.tuple given a lone builder:** FIXED. The error is now named ("expects an array of builders").
- **assertBuilder vs a throwing Proxy:** FIXED (try/catch). The named error still surfaces.
- **README table row:** FIXED.
- **CHANGELOG:** the `unwrap` contract change, the new exports and the size delta are now recorded. The "~8kB" claims are updated to ~9kB.
- **Internal exports:** `validateResolved`, `AMBIGUOUS` and `AMBIGUOUS_MESSAGE` are `@internal`, and `--stripInternal` removes them from the published `.d.ts`. `BUILDER` and `isBuilder` are public and documented.
- **tjs-lang blast radius:** we ran the consumer suites against the 1.12.0 tarball in scratch clones. tosijs (1043/0) and tosijs-ui (1540/0) are unchanged. tjs-lang is also unchanged: 5962 pass, and the one failure, its own tarball `files` check, fails identically on its current 1.5.1. We filed tjs-lang#58 (board #2416) for its local unwraps.
- **Follow-ups filed to the board:** a real cross-version builder test, size deltas in the pack output, and the practices lesson (a refusal must be checked at every internal re-entry).
