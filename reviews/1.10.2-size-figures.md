`/Users/tonioloewald/tosijs-schema/llms.txt:50`:

```
- Tree-shakeable: `sideEffects: false`, per-concern modules. Named imports
  shake to ~1–4.6kB; `tosijs-schema/infer` is a self-contained ~1.5kB subpath.
```

`4.6` is the pre-fix `agentContract` number this release corrected to `5.5` in the README table. Measured independently at HEAD with `make-coverage.ts`'s own method (one-line re-export shim → `bun build --minify --target=node` → `gzip -9`): validate 3,543 B, `s` 3,536 B, filter 4,142 B, agentContract 5,586 B, everything 8,438 B, `dist/infer.js` 1,549 B. - `package.json files` is `["dist","CHANGELOG.md","llms.txt"]` — it lands in the tarball, next to a CHANGELOG that names this exact number as the defect being fixed. The published package contradicts itself on its own headline fix.
- It is the agent-facing doc; an agent reading the installed package gets a bundle budget 17% low.
- CLAUDE.md requires llms.txt be updated every release; `git diff v1.10.1...HEAD -- llms.txt` shows the only change is the version header.
- `make-context.ts` stamps only llms.txt's version header and `make-coverage.ts` targets README rows only, so `git status --porcelain` stays clean with the wrong number in it — the drift gate structurally cannot see this line.
- Known and missed: `reviews/1.10.0-pass5-final.md:110` (F5) names this file verbatim. `git log -S "4.6kB" -- llms.txt` shows the figure entered at v1.6.0 and has shipped through eight tags; two of those were after a review flagged it. `TODO.md`'s closed item scopes the fix to the README only.

**Fix:** set the range to **`~3.5–5.5kB`**, not `~1.5–5.5kB` — no *named import* is ~1.5 kB; the floor for a named import is 3.5 kB (`validate`/`s`), and `~1.5kB` is the subpath, which the same sentence already names separately. The current line is wrong at both ends.

**Re-review scope: Tier 0 only** (mechanical doc correction) — re-run `bun run pack`, confirm `git status --porcelain` is empty. If you also teach `make-coverage.ts` to stamp that llms.txt sentence (recommended — it already computes the numbers), Tier 0 plus one confirmation that the drift gate is still clean.

## Majors (3)

### M1 — README:458 guarantees "every figure in the table is measured at build time"; two of the figures it covers are not *(correctness + efficiency + blast-radius, verified)*

`README.md:458` (new in this diff) asserts: *"Every figure in the table is **measured at build time** and regenerated by `bun run pack`, so it cannot drift from what you actually get."*

`make-coverage.ts:71` measures four entry points (`validate`, `s`, `filter`, `agentContract`) plus a separate `everything` replaceLine — five of six rows. The `inferSchema` (from `tosijs-schema/infer`) row is stamped by nothing, and its bold `**~1.5 kB**` would not even match the loop's `~[\d.]+ kB` regex if someone naively added it to `ENTRY_POINTS` (it would throw "could not find per-import size row"). `bun run show-size` prints `dist/infer.js`'s size to the console and deletes the artifact — eyeball-only, no gate. The same sentence also names `diff` in the "3.5–4 kB range"; `diff` is an exported entry point and is not measured either.

Both numbers are correct **today** (`dist/infer.js` 1,540–1,549 B; `diff` shim 3,969–3,975 B), so no reader is currently misled by the table — the false half is the guarantee. And the drift is not hypothetical on that exact row: at v1.7.0 `dist/infer.js` was 1,583 B (1.55 kB) while the README claimed ~1.4 kB. `~1.5kB` is also the most-repeated claim in the repo (README ×3, CONTEXT.md:45, llms.txt ×3) — the single row most worth gating is the one left out.

**Recommendation: fix in the same pass as B1, pre-tag.** Preferred: add `inferSchema` (sized from `dist/infer.js`, with its own bold-aware `replaceLine`) and `diff` to the measured set, so the sentence becomes true as written. Cheap alternative: narrow the sentence to name which rows are generated — but a half-true guarantee is precisely what this release exists to retire, so prefer closing the gap. Not counted as a blocker only because nothing it states is numerically wrong for a reader today.

### M2 — `pattern` runs untrusted regexes against untrusted values with no complexity or length bound *(security, verified; PRE-EXISTING, does not block)*

`src/formats.ts:80` (`compilePattern`). Reproduced through the shipped `dist/index.js` on Node v22.22.1: `{type:'string', pattern:'^(a+)+$'}` against `'a'.repeat(31)+'!'` takes **16,240 ms**, doubling per added byte (26 B = 1.2 s, 32 B = 16 s, 35 B ≈ 2 min). Two reachable paths: the marketed "plain JSON schema off the wire" `validate` path, and `agentContract` — `unenforcedKeywords({type:'string',pattern:'^(a+)+$'})` returns `[]`, the gate **accepts** the schema at construction, and `gate.check(...)` then burns 16,931 ms on an agent-supplied value. An unauthenticated hang of the capability gate, with the honesty seam reporting "nothing unenforced here".

Structurally invisible to the suite: Bun/JSC's backtrack limiter plateaus at ~475 ms regardless of length, so `bun test` can never observe it. There is no hostile-pattern test anywhere. `maxLength` *is* checked before `pattern` (`src/schema.ts:739-745`) and neutralizes it — nothing requires or suggests one. The library's own 13 built-in formats are safe (all <20 ms on adversarial input); this needs a consumer-authored naive regex.

Pre-existing (`src/formats.ts`/`src/schema.ts` byte-identical to v1.10.1) and scoped in `TODO.md:265` as "scoped 2026-09-14, **NOT yet implemented**". The full fix needs its own release. **But the already-decided documentation half has not shipped either** — grep finds no trust-boundary caveat in README, CONTEXT.md, llms.txt or CHANGELOG, and `TODO.md` is not in `files`, so the only record of this is invisible to consumers. README's "A note on `eval` and security" (line 246) claims a security advantage over Ajv/TypeBox on exactly the untrusted-schema path, and the fail-closed paragraph (line 499) advertises that *invalid* patterns are refused without noting that valid-but-exponential ones are not. Adding that caveat is in-genre for a docs patch and should ride this release.

*(One correction to the finding as filed: the reported "82,687 ms at 32 bytes" did not reproduce — 16,240 ms on the verification box. Constant factor is machine-dependent; the exponential shape reproduced identically across three independent measurements.)*

### M3 — `schema`-key duck-type unwrap is still live in core `validate`/`filter` *(security, verified; PRE-EXISTING and disclosed, does not block)*

`src/schema.ts:606` (and `:888` in `filter`): `const schema = (builderOrSchema as any)?.schema || builderOrSchema`, before any allowlist. Reproduced at HEAD: `validate(42, {type:'object',properties:{a:{type:'string'}},required:['a'],additionalProperties:false,schema:true})` → **true**; same for `'pwned'`; `filter({nope:1}, thatSchema)` → `{"nope":1}` unstripped. No adversary needed — `schema` is not a JSON Schema keyword, so a wire/DB schema tagged `{"type":"object","properties":{...},"schema":"v1"}` collapses the same way (a `"schema"`-for-`"$schema"` typo does it too).

Two refinements found during verification, neither rescuing it: the collapse only happens at the entry point (a stray `schema` key nested under `properties` is harmless), and the operator is `||` not `??`, so falsy values fall through safely.

1.10.0 fixed this in the gate (`src/contract.ts:116` `isBuilder` now requires a real `validate` method, pinned at `contract.test.ts:897-914`); the identical hole in the core validator has **no test at all**, and `validate`/`filter` are the far more used entry points — one package, two different answers to the same question. Deliberately deferred: tightening `validate` is BREAKING under this repo's versioning threshold and is owed its own release + migration note, and it is disclosed at `CHANGELOG.md:142`. Disclosure is not remediation, so it stays scheduled.
